# Интеграция модуля обратной связи

## Статус и область применения

Этот репозиторий содержит автономный PHP/MariaDB-модуль с виджетом обратной связи, API записи ответов и демонстрационной админкой. Это не готовая интеграция с LIMIS: модуль пока не подключён к настоящей авторизации, языковым настройкам, страницам и бизнес-процессам LIMIS. Пример сайта в `public/index.php` — только демонстрационная оболочка.

Фронтенд сайта может быть написан на любой технологии. Веб-страница встраивает JavaScript и CSS виджета, а PHP API модуля работает на сервере и сохраняет ответы в MariaDB. Для текущей реализации необходимы PHP с `pdo_mysql` и MariaDB; другая СУБД не поддерживается без изменения кода и миграций.

Эта инструкция описывает текущее поведение и рекомендуемый путь интеграции. Она не подтверждает совместимость с конкретной установкой LIMIS, соответствие требованиям доступности или требованиям законодательства о персональных данных.

## Что нельзя завершить без дополнительной информации или исходного кода

### Ограничения, которые важно учитывать

- Текущий админ-интерфейс и экспорт CSV защищены демонстрационной сессией, а не ролью из LIMIS. Подключение только страницы обзора недостаточно: защищать нужно каждый запрос к админке, включая экспорт.
- Виджет не передаёт в API LIMIS-логин, ID пользователя или PHP-сессию. Он передаёт ответы, язык, группу страницы и stateless-токен. Сервер использует адрес клиента для ограничения частоты: сохраняется HMAC-ключ, а не открытый IP; запись перестаёт учитываться через час и физически удаляется при ближайшем запуске очистки. Веб-сервер или прокси при этом могут отдельно вести access-логи с IP.
- При работе за reverse proxy PHP сейчас использует `REMOTE_ADDR`, видимый PHP. Код не читает `X-Forwarded-For`. Если все запросы приходят с адреса прокси, ограничение частоты может применяться к этому адресу для всех посетителей. Нельзя просто доверять переданному клиентом `X-Forwarded-For`; корректную обработку должен настроить владелец доверенного прокси и проверить разработчик.
- Панель показывает не более 100 последних комментариев за выбранный период; пагинации пока нет.
- Срок хранения 180 дней задан в SQL-команде очистки. Изменение срока требует согласования и соответствующего изменения/проверки очистки.
- Язык, история просмотренных страниц и подавление приглашения хранятся в `localStorage` браузера. Пользователь может очистить эти данные; разные домены и поддомены имеют разное хранилище.

## Рекомендуемая схема размещения

Предпочтительный вариант — разместить PHP-модуль на том же origin, что и сайт, например:

```text
https://limis.example.ee/feedback/tagasiside/widget.js
https://limis.example.ee/feedback/tagasiside/widget.css
https://limis.example.ee/feedback/tagasiside/token.php
https://limis.example.ee/feedback/tagasiside/submit.php
```

Это можно сделать отдельным PHP-приложением за reverse proxy. Важно, чтобы все четыре файла виджета и API были доступны в одном каталоге: JavaScript определяет адрес `token.php` и `submit.php` относительно URL самого `widget.js`.

Размещение на отдельном домене возможно, но потребует отдельной настройки CORS для `token.php` и `submit.php`. Запрос отправки использует `Content-Type: application/json`, поэтому браузер обычно сначала отправит preflight-запрос `OPTIONS`. Текущий `submit.php` принимает только `POST`, а CORS middleware/ответы `OPTIONS` в проекте не настроены. Это потребует изменений серверной конфигурации или кода. Как минимум, серверу нужно разрешить точный origin LIMIS, методы `GET`, `POST`, `OPTIONS` и заголовок `Content-Type`, включая необходимые CORS-заголовки в ответах на preflight и фактические запросы. Разрешайте только точные доверенные origin LIMIS, а не `*`; cookie авторизации LIMIS виджету не нужны. Не включайте передачу credentials без отдельного обоснования.

Если основной сайт статический или написан не на PHP, это не препятствие: оставьте PHP API отдельным сервисом и подключите его JavaScript/CSS с сайта. Но для отдельного origin всё равно потребуется CORS. Если нельзя настраивать CORS, используйте same-origin reverse proxy.

## Установка на сервер

1. **Согласуйте владельцев и параметры.** Определите ответственных за админ-доступ, privacy, хранение ответов, языки, страницы, критические процессы и эксплуатацию.
2. **Подготовьте PHP и MariaDB.** Для текущей версии используйте PHP 8.5 с расширением `pdo_mysql` и MariaDB 11. Настройте HTTPS. Убедитесь, что PHP действительно исполняет файлы `.php`.
3. **Разместите приложение.** Корнем веб-сервера должна быть папка `public/`. Папки `config/`, `src/`, `migrations/` и `bin/` не должны быть доступны как статические файлы из интернета. В конфигурации веб-сервера запретите скачивание PHP-конфигурации и внутренних файлов.
4. **Создайте отдельную базу.** Для примера:

   ```sql
   CREATE DATABASE limis_feedback CHARACTER SET utf8mb4;
   ```

   Примените `migrations/001_install.sql` к этой базе. Предпочтительна отдельная схема: таблицы имеют фиксированные имена `limis_tagasiside`, `limis_tagasiside_guard` и `limis_tagasiside_nonce`, которые могут совпасть с таблицами другого экземпляра модуля.
5. **Настройте секреты.** Скопируйте `config/config.example.php` в `config/config.php` вне web-root. Задайте DSN, имя пользователя БД и пароль. Создайте случайный секрет, например:

   ```sh
   php -r "echo bin2hex(random_bytes(32)), PHP_EOL;"
   ```

   Секрет должен быть случайным, приватным и постоянным между запросами; не используйте приведённое в примере значение. Файл `config.php` и секреты нельзя добавлять в Git или отдавать клиенту. При необходимости путь к конфигурации можно передать через переменную окружения `LF_CONFIG`.
6. **Ограничьте права БД.** Миграции выполняйте отдельной учётной записью с правами DDL. Для текущего runtime-пользователя выдайте только права, нужные установленным функциям: API записывает ответы, nonce и guard-записи; админка читает ответы; очистка удаляет старые ответы и просроченные записи. Не используйте учётную запись администратора MariaDB. Учтите, что пример использует одну конфигурационную учётную запись для API, админки и очистки.
7. **Настройте ежедневную очистку.** Выполняйте `php /полный/путь/bin/purge.php` раз в сутки от системного пользователя, которому доступна конфигурация, но не выдавайте этому пользователю лишние права. Linux cron, например:

   ```cron
   0 3 * * * /usr/bin/php /путь/к/проекту/bin/purge.php
   ```

   На Windows создайте задачу в Task Scheduler: программа — полный путь к `php.exe`, аргумент — полный путь к `bin\purge.php`; укажите рабочую папку проекта и сервисную учётную запись. Проверьте результат запуска и журнал ошибок.
8. **Проверьте доступность файлов.** Из браузера или `curl` проверьте, что `widget.js` и `widget.css` отдаются как JavaScript и CSS, `token.php` возвращает JSON без кеширования, а `submit.php` не доступен методом GET (ожидается `405`). Не включайте на production демонстрационные синтетические данные через `bin/seed.php`.

## Встраивание виджета

Подключите CSS в `<head>`, а JavaScript после содержимого страницы, например перед `</body>`:

```html
<link rel="stylesheet"
      href="/feedback/tagasiside/widget.css">

<script defer
        src="/feedback/tagasiside/widget.js"
        data-lang="et"
        data-invite-after-seconds="45"
        data-invite-min-pages="2"></script>
```

Для русской версии передайте `data-lang="ru"`. Значение языка должно браться из текущих настроек сайта; сам виджет не умеет читать неизвестное ему состояние языка LIMIS. Если атрибут отсутствует или имеет другое значение, виджет показывает эстонский интерфейс.

Атрибуты:

| Атрибут | Назначение |
|---|---|
| `data-lang` | `et` или `ru`; задаёт язык вопросов и интерфейса. |
| `data-page` | Необязательная группа страницы. Допустимы только `home`, `eservices`, `procurement`, `property`, `account`, `appointment`. Это значение также отправляется в базу как `page_group`. |
| `data-invite-after-seconds` | Сколько секунд активности накопить до автоматического приглашения. Значение по умолчанию — `45`; допустимо целое число от `0`. |
| `data-invite-min-pages` | Минимальное число различных ключей страниц в локальном хранилище. По умолчанию — `2`; допустимо целое число не меньше `1`. |
| `data-critical="1"` | Начальное состояние важной операции при загрузке страницы: не показывать автоматическое приглашение. Не скрывает постоянную кнопку виджета. |

Указывайте одинаковые пороги на всех страницах сайта: накопленное время и список страниц общие для страниц одного origin. В демо эти параметры заданы в начале `public/index.php`.

### Как считаются страницы

При загрузке скрипт добавляет в список страниц первый подходящий ключ в таком порядке:

1. значение query-параметра `?p=...`, если он есть;
2. `data-page`, если он задан;
3. `location.pathname`, если первые два варианта отсутствуют.

Следствие: если передавать одно и то же `data-page="eservices"` на десяти URL, для порога это будет **одна** страница. Если `data-page` не задан, разные пути считаются отдельно, но в ответе `page_group` будет пустым (`NULL`). Если задать `data-page`, в базу сохраняется только одна из перечисленных групп, а не полный URL.

Текущая реализация не разделяет уникальный ключ посещённой страницы и категорию `page_group`. Для большого сайта, где нужны одновременно точный подсчёт URL/SPA-маршрутов и аналитическая категория, потребуется изменить виджет и API, добавив отдельный атрибут/поле для ключа страницы. Не передавайте произвольный URL в `data-page`: API отклонит неизвестное значение.

Для SPA, где URL меняется без полной загрузки документа, виджет сам не узнаёт о переходе и не добавляет новый ключ страницы. Понадобится расширение API виджета, чтобы приложение сообщало ему о смене маршрута; такого вызова сейчас нет.

## Подавление приглашения во время важных операций

На страницах, где важная операция уже активна при первой загрузке, укажите `data-critical="1"` в теге скрипта. Для операций, которые начинаются и заканчиваются без перезагрузки, используйте API:

```js
if (window.LimisFeedback) {
    window.LimisFeedback.setCritical(true);  // операция началась
}

// После успешного завершения, отмены или ошибки:
if (window.LimisFeedback) {
    window.LimisFeedback.setCritical(false);
}
```

Либо отправляйте событие:

```js
window.dispatchEvent(new CustomEvent('limis-feedback:critical', {
    detail: { active: true }
}));

// После выхода из критического процесса:
window.dispatchEvent(new CustomEvent('limis-feedback:critical', {
    detail: { active: false }
}));
```

Сброс флага должен выполняться во всех исходах операции — успех, отмена и ошибка. Сейчас флаг скрывает автоматическое приглашение и уже показанную плашку приглашения. Постоянная кнопка «Оценить LIMIS» остаётся видимой и открывает форму вручную. Если требование LIMIS состоит в полном скрытии виджета, текущего API недостаточно — это нужно отдельно реализовать и протестировать.

## Настройка CSP и браузерной безопасности

- Разрешите origin виджета в `script-src`, `style-src` и `connect-src` Content Security Policy. При same-origin размещении достаточно соответствующих правил для origin сайта; при отдельном домене добавьте его явно.
- Виджет создаёт элементы с inline-стилями. Строгая CSP с запретом inline style может блокировать часть оформления. Проверьте консоль браузера на тестовой копии; если inline-стили запрещены политикой, потребуется адаптация виджета или политики.
- При кросс-доменном размещении настройте точный CORS allowlist и preflight `OPTIONS`; не открывайте API всем origin.
- Используйте HTTPS. Не передавайте в атрибуты или JSON токены сессии LIMIS, идентификаторы пользователей или данные заявления.
- Обновляйте URL скрипта или его cache-busting версию при публикации обновлений, чтобы браузер не продолжал использовать старый файл.

## Подключение админки к LIMIS

Не открывайте текущую демонстрационную админку в production и не считайте её проверкой роли LIMIS. После получения auth-контракта:

1. Выполняйте штатную авторизацию LIMIS и проверку роли на сервере при каждом запросе админки.
2. Защитите и страницу обзора, и CSV-экспорт; скрытия ссылки в интерфейсе недостаточно.
3. Используйте механизмы сессии и CSRF-защиты, принятые в LIMIS. Не создавайте собственную сессию, которая сама назначает роль `Peakasutaja`.
4. Проверьте logout, истечение сессии, смену/отзыв роли, cookie-флаги и поведение за reverse proxy.
5. Убедитесь, что пользователи без нужной роли получают отказ и не могут получить CSV прямым URL.

Сейчас `token.php` и `submit.php` не используют PHP-сессию LIMIS: токен формируется через HMAC, действует не более двух часов и одноразово учитывается в базе. Это уменьшает связь виджета с сессией сайта, но не заменяет проверку сессии для админки.

## Поля, словари и изменение анкеты

Допустимые языки, цели, результаты, типы затруднений и группы страниц заданы в `src/bootstrap.php`; типы столбцов также заданы в `migrations/001_install.sql`. При изменении вопросов/вариантов синхронно проверьте:

1. варианты и подписи в `public/tagasiside/widget.js`;
2. серверную валидацию в `src/bootstrap.php` и `public/tagasiside/submit.php`;
3. типы/ограничения таблиц и миграцию;
4. подписи статистики в `public/admin/tagasiside.php`;
5. CSV и существующие ответы.

Одного изменения подписи в JavaScript недостаточно: сервер может отклонить новый код ответа, а схема БД может его не принять.

## Данные и конфиденциальность

По умолчанию форма отправляет язык, выбранные ответы, оценку, комментарий до 500 символов и необязательную группу страницы. Она не отправляет идентификатор пользователя LIMIS или содержимое сессии. Свободный комментарий сохраняется как есть; предупреждение в форме не является фильтром. Перед запуском решите, допустим ли свободный текст, кто может видеть его в админке/экспорте и как реагировать на случайно указанные персональные данные.

Ответы старше 180 дней удаляются только при запуске `bin/purge.php`. Проверьте, что этот срок соответствует утверждённой политике, настройте задачу и подтвердите удаление на тестовой БД. Учитывайте резервные копии, журналы веб-сервера и выгруженные CSV: очистка основной базы не удаляет их автоматически.

## Проверки перед production

Проводите проверку на staging и отдельной тестовой БД, не добавляя тестовые ответы в production:

- Виджет и CSS загружаются по HTTPS; API доступны из того же каталога.
- Правильный язык передаётся при переключении ET/RU.
- Автоприглашение появляется только после порогов времени и страниц; время считается только при видимой вкладке.
- Повторно проверьте порог для обычных страниц, страниц одной группы, query-параметра `p` и SPA-переходов.
- Во время каждой критической операции автоматическое приглашение подавлено; флаг снимается после успеха, отмены и ошибки. Проверьте также поведение постоянной кнопки.
- На тестовой БД проверьте валидную отправку, одноразовый токен, дубликат, лимит отправок, сбой БД и корректную реакцию формы.
- Проверьте авторизацию роли для админки и CSV прямыми запросами, а не только через меню.
- Подтвердите ежедневную очистку и фактический срок хранения.
- Проверьте CSP, CORS (если cross-origin), консоль браузера, мобильные размеры, клавиатурную навигацию, скринридер и доступные языки.

Текущие результаты ограниченных локальных проверок и явно невыполненные проверки перечислены в `README.md`.
