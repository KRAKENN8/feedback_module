# Установка и интеграция модуля обратной связи

## 1. Статус и схема работы

Репозиторий содержит самостоятельный PHP-модуль: браузерный виджет, публичный API, таблицы MariaDB, административный обзор и CLI-команду очистки. Основные компоненты готовы для интеграции, но подключение к настоящим страницам и авторизации LIMIS ещё не выполнено. Для публикации на LIMIS нужны действия ответственного разработчика и проверки в тестовом контуре.

Обычная отправка отзыва проходит так:

1. Страница загружает `widget.js` и `widget.css`.
2. При открытии формы браузер запрашивает одноразовый токен у `token.php`.
3. После заполнения `widget.js` посылает JSON в `submit.php`.
4. `submit.php` проверяет поля, токен и лимит, затем записывает ответ в MariaDB.
5. Администратор просматривает статистику через `/admin/tagasiside.php`.
6. Планировщик операционной системы запускает `bin/purge.php`, который удаляет ответы старше 180 дней и истёкшие технические записи.

Внешние сервисы опросов и аналитики не используются. Обслуживание API виджета не запускает PHP-сессию и не получает LIMIS ID пользователя.

## 3. Требования перед установкой

- PHP 8.5 с включённым `pdo_mysql` и `mbstring`.
- MariaDB 11.
- Redis (опционально, рекомендуется для кратковременных счётчиков rate limiting 3 ответа/час).
- HTTPS для публичного сайта.
- Возможность настроить корень веб-сервера и расписание CLI-задач.
- Выделенные ответственное лицо за админ-доступ, privacy и безопасность.

До установки согласуйте:

1. разрешённые публичные страницы и момент вызова API критической операции;
2. источник языка ET/RU на сайте;
3. допустимость свободного комментария и обработку персональных данных в нём;
4. срок хранения ответов и резервных копий;
5. правила организации для E-ITS, хранения журналов, резервного копирования и реакции на инциденты;
6. кто в LIMIS имеет роль `Peakasutaja` и как приложение проверяет эту роль.

## 4. Развёртывание PHP и базы данных

### 4.1. Разместите файлы за пределами публичного корня

Рекомендуемая структура:

```text
/srv/limis-feedback/
  config/config.php
  src/bootstrap.php
  migrations/
  bin/
  public/
    tagasiside/
    admin/
```

Настройте веб-сервер так, чтобы документ-корнем был только каталог `public/`. Папки `config/`, `src/`, `migrations/` и `bin/` нельзя отдавать как статические файлы. На существующем сайте подключайте только нужные маршруты модуля через виртуальный каталог или reverse proxy.

`public/index.php` и `public/site.css` — оболочка для локальной проверки страниц. При интеграции замените её действующим сайтом; не подменяйте ею главную страницу LIMIS.

### 4.2. Создайте отдельную базу и примените схему

Создайте отдельную базу `utf8mb4`, например:

```sql
CREATE DATABASE limis_feedback CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

Примените `migrations/001_install.sql` только к этой базе. Имена таблиц фиксированы:

- `limis_tagasiside` — ответы;
- `limis_tagasiside_nonce` — использованные токены.

Отдельная база предотвращает конфликт таблиц с другим приложением или экземпляром модуля.

### 4.3. Создайте рабочую конфигурацию и секрет

Скопируйте `config/config.example.php` в `config/config.php` вне веб-корня. Укажите DSN, пользователя и пароль MariaDB. Сгенерируйте секрет длиной не менее 32 случайных байт:

```powershell
php -r "echo bin2hex(random_bytes(32)), PHP_EOL;"
```

или:

```sh
php -r "echo bin2hex(random_bytes(32)), PHP_EOL;"
```

Сохраните полученную hex-строку в `secret`; не используйте значение из примера и не меняйте секрет между обычными запросами. Рабочий конфигурационный файл исключён из Git. Если файл хранится в другом месте, задайте переменную окружения `LF_CONFIG` для PHP-FPM/веб-сервера и отдельной CLI-задачи.

Rate limit целиком обслуживается Redis (`redis_enabled => true`): не более трёх успешно записанных ответов с одного `REMOTE_ADDR` за час. Ключ адреса HMAC-производный, а в Redis хранятся уникальные nonce токенов. Если запись в MariaDB не удалась, резерв снимается; при аварийном завершении процесса резерв может сохраняться до истечения часового TTL. Redis-клиент поддерживает TCP и пароль через `redis_pass`, но не TLS/Redis ACL username: используйте закрытую доверенную сеть, firewall и отдельные учётные данные.

Если Redis недоступен или вернул ошибку, endpoint возвращает `503 Service Unavailable` (fail-closed защита), предотвращая спам-атаки в моменты отказа кэширующего сервиса. Новые Redis-ключи используют версию `v2`, поэтому старые строковые счётчики не конфликтуют и истекут самостоятельно.

`admin_hash` предназначен только для текущего отдельного тестового входа. Создать хеш можно командой:

```powershell
php -r "echo password_hash('replace-with-a-long-password', PASSWORD_DEFAULT), PHP_EOL;"
```

Не добавляйте пароль или его хеш в публичный репозиторий.

### 4.4. Права MariaDB (принцип наименьших привилегий)

Миграции (`001_install.sql`) выполняйте отдельной учётной записью администратора БД с правами DDL (`CREATE TABLE`, `INDEX` и т.д.). Для runtime-пользователя приложения нужны **только минимально необходимые права** на таблицы данного модуля:

- `SELECT` — чтение статистики и проверка токенов nonce;
- `INSERT` — запись ответов и использованных nonce;
- `DELETE` — регламентное удаление устаревших данных скриптом `bin/purge.php`;
- `LOCK TABLES` — взятие консультативной блокировки MariaDB (`GET_LOCK`) при регламентной очистке (`purge.php`).

Пример настройки прав пользователя приложения (проверено на тестовом стенде):

```sql
-- Отзыв всех глобальных привилегий и прав DDL
REVOKE ALL PRIVILEGES ON limis_feedback.* FROM 'limis_feedback_app'@'localhost';

-- Выдача исключительно требуемых прав DML и блокировок
GRANT SELECT, INSERT, UPDATE, DELETE, LOCK TABLES ON limis_feedback.* TO 'limis_feedback_app'@'localhost';

-- Применение изменений
FLUSH PRIVILEGES;
```

Убедитесь, что пользователю приложения не выданы права `DROP`, `ALTER`, `GRANT` или доступ к другим базам данных сервера. Не применяйте rollback-скрипт к рабочей базе до подтверждённой процедуры деинсталляции и создания полной резервной копии.

### 4.5. Включите безопасный режим PHP

В рабочем PHP/FPM/Apache окружении отключите показ исключений посетителям (`display_errors=Off`), включите серверное логирование ошибок и ограничьте доступ к файлу журнала. Endpoint отправки возвращает посетителю общий ответ при сбое, а причина должна оставаться в журнале сервера. Проверяйте, что пароли и секреты не попадают в логи.

## 5. Встраивание в сайт

Предпочтительно, чтобы файлы виджета и API были на том же origin, что и сайт. Если сервер сайта проксирует приложение под `/feedback/`, разместите комплект по единому маршруту, например:

```text
https://site.example/feedback/tagasiside/widget.js
https://site.example/feedback/tagasiside/widget.css
https://site.example/feedback/tagasiside/token.php
https://site.example/feedback/tagasiside/submit.php
```

JavaScript вычисляет адрес API относительно URL `widget.js`; поэтому `token.php` и `submit.php` должны быть рядом с ним.

Добавьте CSS в `<head>`, а скрипт — после содержимого страницы:

```html
<link rel="stylesheet" href="/feedback/tagasiside/widget.css">
<script
  defer
  src="/feedback/tagasiside/widget.js"
  data-lang="et"
  data-page="eservices"
  data-page-key="service-search"
  data-invite-after-seconds="45"
  data-invite-min-pages="2"></script>
```

На русской версии передайте `data-lang="ru"`. На всех страницах одного origin используйте одинаковые настройки порога. Виджет показывает постоянную кнопку; автоматическое приглашение появляется после указанного времени и количества различных ключей страниц.

### Определение языка и совместимость с LIMIS (`localStorage` и URL)

В LIMIS текущий язык хранится в браузере в **`localStorage`** под ключом **`language`** (`'et'` или `'ru'`), а в адресной строке передаётся параметром `?lang=ru` (например, `https://limis.narva.ee/start/main.php?lang=ru`).

Модуль полностью совместим с этой схемой:
1. **Приоритет определения языка в виджете:**
   - Параметр в URL: `?lang=ru` или `?lang=et` (напрямую из адресной строки LIMIS).
   - Атрибут тега скрипта: `data-lang="ru"` или `data-lang="et"`.
   - Значение из `localStorage`: `localStorage.getItem('language')` (`'et'` или `'ru'`).
   - Атрибут документа: `<html lang="ru">`.
   - Значение по умолчанию: `'et'`.
2. **Синхронизация `localStorage`:** при инициализации или смене языка виджет автоматически синхронизирует выбранный язык в `localStorage.setItem('language', lang)`. Локальная тестовая оболочка (`public/index.php`) также проверяет `localStorage.getItem('language')` при переходе без параметров и сохраняет выбор пользователя.
3. **Динамическое переключение языка в SPA:**
   ```js
   window.LimisFeedback?.setLanguage('ru'); // или событие 'limis-feedback:lang'
   ```

### Простое объяснение адреса страницы, `data-page` и `data-page-key`

- **URL** — адрес страницы в браузере, например `https://site.ee/services/search`. В локальной оболочке параметр `?p=home` после вопросительного знака означает выбранную страницу оболочки.
- **`data-page`** — категория раздела, например `eservices`. Она отправляется с отзывом и записывается в `page_group`. Допустимы только категории, перечисленные в `src/bootstrap.php`.
- **`data-page-key`** — уникальное короткое имя конкретной страницы, например `service-search`. Оно нужно только браузеру для подсчёта разных страниц; на сервер и в таблицу ответов не отправляется.

Используйте разные `data-page-key` для разных публичных страниц, даже если у них одна категория:

```html
<script src="/feedback/tagasiside/widget.js"
        data-lang="ru"
        data-page="eservices"
        data-page-key="service-search"></script>
```

Для другой страницы того же раздела задайте, например, `data-page-key="application-guide"`, сохранив `data-page="eservices"`. Тогда посетитель пройдёт две разные страницы, а в ответе сохранится только категория `eservices`. Не передавайте полный URL, номера заявлений, ID, токены или персональные сведения.

Приоритет ключа для подсчёта: `data-page-key`, затем query-параметр `?p=` (используется локальной оболочкой), затем путь страницы. На реальном сайте задавайте стабильный безопасный `data-page-key`, чтобы query-параметры и потенциально чувствительный путь не попадали даже в локальное хранилище браузера.

В приложении SPA при каждом виртуальном переходе вызовите:

```js
window.LimisFeedback?.setPage('application-guide');
```

Имя добавляется только в список браузера. Категорию для базы по-прежнему задаёт `data-page`.

### Важные операции

При загрузке страницы, где уже выполняется важная операция, задайте `data-critical="1"`. Для операции, которая начинается позднее:

```js
window.LimisFeedback?.setCritical(true);
// После успеха, отмены и ошибки:
window.LimisFeedback?.setCritical(false);
```

Не забудьте сбрасывать состояние во всех исходах. Сейчас оно отключает только автоматическое приглашение; постоянная кнопка остаётся доступной. Реальные точки начала и окончания операций должен подключить разработчик тех экранов LIMIS, так как их исходный код здесь отсутствует.

### Если API размещён на другом домене

Текущая конфигурация CORS не добавлена. Браузерная отправка JSON вызовет preflight `OPTIONS`. Понадобится настройка API/proxy для точного allowlist origin, методов `GET`, `POST`, `OPTIONS`, заголовка `Content-Type` и соответствующих CORS-заголовков. Не используйте `Access-Control-Allow-Origin: *` для административных маршрутов и не передавайте cookie LIMIS в публичные запросы виджета. Если CORS менять нельзя, используйте same-origin reverse proxy.

Проверьте CSP сайта: разрешите хост виджета в `script-src`, `style-src`, `connect-src`. Виджет не требует inline-атрибутов стиля; CSP сайта также должна разрешать собственный код интеграции. Не меняйте широкие production-политики CSP без согласования с владельцем LIMIS.

## 6. Административная страница и подключение к LIMIS

### Что реализовано и подготовлено для интеграции ролей

В модуле выделен единый компонент авторизации [src/AdminAuth.php](file:///c:/Users/kraken/Downloads/limis-feedback/src/AdminAuth.php), который поддерживает два режима работы (`auth_mode` в `config.php`):
1. **`'standalone'` (по умолчанию):** автономный режим разработки. Если пользователь ещё не авторизован, показывается экран ввода тестового пароля. При входе в сессию выставляется роль `Peakasutaja`.
2. **`'limis'`:** штатный режим LIMIS. Отключает отдельную форму ввода пароля и выполняет прямую серверную проверку прав текущей сессии LIMIS.

#### Поддержка сессий и ролей LIMIS:
- `AdminAuth` автоматически проверяет ключи сессии, используемые в LIMIS:
  - `$_SESSION['active_role']` (имя скрытого поля из формы логина LIMIS `Konto valimine`),
  - `$_SESSION['role']`,
  - `$_SESSION['user']['role']`,
  - `$_SESSION['user_role']`.
- Проверка роли `Peakasutaja` выполняется **регистронезависимо** (`'peakasutaja'`, `'Peakasutaja'`, `'PEAKASUTAJA'`), а также поддерживает составные идентификаторы (например, `peakasutaja:100`).
- **Обработка неавторизованного доступа (HTTP 403 Forbidden):**
  Если пользователь авторизован в LIMIS под другой ролью — например, как обычный служащий (`kasutaja` / `teenistuja`) или частное лицо (`kodanik_er`) — модуль блокирует доступ к дашборду и CSV с HTTP 403 и отображает экран `tagasiside-forbidden.view.php` с сообщением:
  > *«Teil puudub roll Peakasutaja (aktiivne roll: kasutaja). Pöörduge peakasutaja poole.»*  
  > *(«Требуется роль Главного пользователя. Обратитесь к главному пользователю»)*.
- Если сессия LIMIS уже запущена родительским приложением, модуль не пытается перезапустить её повторно (`session_status() === PHP_SESSION_NONE`), предотвращая конфликты cookie и заголовков.

### Переключение на штатную авторизацию LIMIS

Для переключения в рабочий режим на сервере LIMIS:
1. Задайте в `config/config.php`:
   ```php
   'auth_mode' => 'limis',
   ```
2. Убедитесь, что сессия LIMIS стартует до обращения к `public/admin/tagasiside.php` (или шарится через общие cookie домена) и содержит ключ роли со значением `peakasutaja` (например, `$_SESSION['active_role'] = 'peakasutaja'`).
3. Если LIMIS и модуль обратной связи размещены на разных поддоменах (например, `limis.narva.ee` и `tagasiside.narva.ee`), настройте общую область видимости сессионных cookie в `php.ini` или перед стартом сессии:
   ```ini
   session.cookie_domain = ".narva.ee"
   session.cookie_path = "/"
   session.cookie_secure = 1
   session.cookie_httponly = 1
   session.cookie_samesite = "Lax"
   ```
4. Если сессия LIMIS хранится в нестандартном хранилище (Redis / отдельная БД), подключите обработчик сессий LIMIS перед выполнением `public/admin/tagasiside.php`.

Вся логика проверки прав выполняется компонентом `AdminAuth`:
- При отсутствии активной сессии или роли, отличной от `Peakasutaja`, модуль отдаёт HTTP 403 Forbidden и экран `tagasiside-forbidden.view.php` (для CSV-экспорта отдаётся голый 403 Forbidden).
- Никакие аналитические данные или отзывы не отдаются до успешного прохождения проверки.

## 7. Автоматический запуск `purge.php`

### Что именно удаляется

`bin/purge.php` удаляет:

- ответы из `limis_tagasiside`, которым больше 180 дней;
- истёкшие строки из `limis_tagasiside_nonce`.

Порог 180 дней задан в SQL-коде, а не в расписании. Если ответственное лицо утвердит другой срок, необходимо изменить код и заново проверить его на тестовой базе. Ответы удаляются физически только после запуска задания. Приложение использует даты истечения для расчёта лимитов и без очистки, но таблицы будут расти.

Сценарий возвращает ненулевой код при сбое, пишет причину в системный PHP error log и печатает число удалённых записей. Одновременный запуск блокируется MariaDB advisory lock. При сбое задание должно повторить запуск, а ответственный — проверить журнал.

### Windows Task Scheduler

1. Убедитесь, что MariaDB запускается как служба и доступна под заданной runtime-учётной записью.
2. Проверьте вручную из PowerShell от имени сервисного пользователя:

   ```powershell
   & 'C:\path\to\php.exe' 'C:\path\to\project\bin\purge.php'
   $LASTEXITCODE
   ```

   При успехе последняя команда возвращает `0`. Сообщение должно содержать число удалённых ответов и технических записей. Если конфигурация не лежит по пути `config/config.php`, задайте `LF_CONFIG` для процесса задачи.
3. Откройте **Task Scheduler → Create Task**.
4. На вкладке **General** укажите сервисную учётную запись, включите запуск независимо от входа пользователя и выдайте только необходимые права на чтение конфигурации, запуск PHP и подключение к БД.
5. Создайте отдельный каталог журнала вне `public/`, например `C:\ProgramData\LimisFeedback\logs`, и разрешите запись туда только сервисному пользователю и администраторам.
6. На вкладке **Triggers** создайте ежедневный триггер, например на 03:00 по часовому поясу сервера. Убедитесь, что часовой пояс/летнее время соответствуют принятой политике.
7. На вкладке **Actions** укажите:
   - Program: полный путь к `php.exe`;
   - Arguments: полный путь к `bin\purge.php`;
   - Start in: корень проекта (необязательно, но полезно для администрирования).
8. Если нужно сохранить stdout в файл, вместо PHP укажите `C:\Windows\System32\cmd.exe`, а в Arguments задайте (подставьте свои полные пути):

   ```text
   /d /s /c ""C:\path\to\php.exe" "C:\path\to\project\bin\purge.php" >> "C:\ProgramData\LimisFeedback\logs\purge.log" 2>&1"
   ```

   Каталог журнала нужно создать заранее. Настройте ротацию/срок хранения файла; журнал не должен быть внутри веб-корня.
9. В **Settings** включите запуск как можно скорее после пропущенного расписания, повтор при ошибке с ограниченным числом попыток и запрет параллельного запуска нового экземпляра. Укажите, что делать при длительном выполнении.
10. В свойствах задачи включите журнал истории. Настройте PHP `error_log` в каталог вне веб-корня и ограничьте доступ к нему. Задача должна запускаться от пользователя с чтением конфигурации, доступом к PHP и только необходимыми правами MariaDB.
11. После первого расписания проверьте **Last Run Time**, **Last Run Result = 0**, вывод команды и наличие удалённых старых строк в тестовой базе. Проверяйте также работу после перезагрузки сервера и пропущенного запуска.

Не запускайте эту задачу с правами администратора БД или интерактивного личного пользователя без необходимости. Не размещайте журнал внутри публичного каталога `public/`.

### Linux cron

Создайте задачу в crontab пользователя, которому доступны PHP, конфигурация и база:

```cron
0 3 * * * /usr/bin/php /srv/limis-feedback/bin/purge.php >> /var/log/limis-feedback-purge.log 2>&1
```

Укажите правильный путь к PHP и проекту; для `LF_CONFIG` задайте окружение в защищённом wrapper-файле, который читается только сервисным пользователем. Настройте ротацию `/var/log/limis-feedback-purge.log`, проверьте часовой пояс сервера, выполните команду вручную, а после планового запуска проверьте exit code и журнал. В системах с systemd можно использовать service+timer с `Persistent=true`, ограничениями пользователя и просмотром через `journalctl`.

Ежедневно проверяйте не только факт запуска планировщика, но и успешный код завершения. Резервные копии, CSV, веб-серверные логи и PHP-журналы этой командой не очищаются; у них должны быть отдельные согласованные сроки хранения.
